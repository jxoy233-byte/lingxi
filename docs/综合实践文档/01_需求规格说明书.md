## 第1章 引言

### 1.1 编写目的

### 1.1 编写目的

本文档是"智析（Zhixi）多智能体数据分析对话系统"（以下简称"本系统"或"智析"）的**需求规格说明书**（Software Requirements Specification，SRS）。本文档用于：

1. 明确本系统的功能范围、性能指标与运行环境；
2. 通过面向对象建模（UML）方法建立可视化的系统需求模型，作为后续设计与开发的依据；
3. 作为综合实践答辩评审的核心文档，并为概要设计说明书、详细设计说明书提供需求基线，使后续工作可追溯、可验证。

本文档面向的读者包括：项目开发团队、课程评审教师、后续维护人员。

### 1.2 项目背景

随着大语言模型（LLM）与多智能体（Multi-Agent）技术的快速发展，传统的"一问一答"式对话系统已难以满足数据分析、学术研究、产品决策等场景对**复杂推理、多模态解析、可执行代码验证、跨会话记忆**等方面的需求。用户在日常工作中常常面临以下痛点：

- **工具切换繁琐**：需要在聊天窗口、Python IDE、Excel、文档阅读器之间反复切换；
- **上下文易丢失**：多轮对话后模型容易"遗忘"早期信息；
- **执行环境不可控**：让 LLM 直接执行系统命令存在数据泄露、误操作等安全隐患；
- **格式单一**：仅支持纯文本交互，无法解析 PDF、Excel、图片中的结构化信息；
- **跨平台不便**：纯 Web 端无法在内网或离线环境使用。

"智析（Zhixi）"是为解决上述痛点而设计的**多智能体数据分析对话系统**。它通过多智能体协同框架实现复杂任务的拆解与编排，借助容器化沙盒实现隔离的代码执行，借助持久化存储实现会话状态与长期记忆，借助文档解析与视觉语言模型实现多模态理解，最终通过浏览器与桌面客户端两种形态对外提供服务。

## 第2章 项目概述

### 2.1 项目目标

本系统的总体目标是：**构建一个面向数据分析场景的多智能体对话系统，在保证安全与可控的前提下，提供对话、文件解析、代码执行、记忆管理、可视化预览的端到端能力**。具体目标分解如下：

| 目标编号 | 目标描述 | 衡量指标 |
|----------|----------|----------|
| G1 | 多智能体协同推理：基于状态图框架构建可循环、可中断、可回溯的对话工作流 | 单会话工具调用循环 ≥ 20 轮稳定 |
| G2 | 安全的代码执行：通过容器沙盒池隔离用户代码，单次执行限时 | 沙盒容器池大小 ≥ 2，并发安全 |
| G3 | 多模态文档解析：支持 PDF / Word / PPT / Excel / CSV / 图片等多种格式 | 支持格式 ≥ 6 种，图片走 VL 模型 |
| G4 | 流式响应：基于 SSE 的 token 级流式输出 | 首 token 延迟 ≤ 2 秒 |
| G5 | 会话状态持久化：支持 checkpoint 与断点恢复 | 中断后可完整恢复上下文 |
| G6 | 跨平台客户端：Web 与桌面端双形态 | 支持三大桌面平台打包 |
| G7 | 长期记忆管理：跨会话上下文压缩与检索 | 每轮结束后台异步压缩 |
| G8 | 高危命令防御：拦截危险系统命令 | 拦截规则覆盖常见高危操作 |

### 2.2 软件范围

#### 2.2.1 软件包含的功能

1. **对话与推理**
   - 多轮对话、流式 SSE 输出、思考过程可视化；
   - 输入优化：调用 LLM 改写用户输入以提升推理质量；
   - 多 LLM 服务商切换；
   - 终止生成与重新生成。

2. **会话管理**
   - 新建、列出、删除会话；
   - 会话标题修改；
   - 会话回溯：回到任一历史检查点；
   - 会话中断与续接。

3. **文件与多模态**
   - 多格式文件上传：PDF、Word、PPT、Excel、CSV、图片、Markdown、JSON、XML、纯文本；
   - 文档解析：通用文档解析 + 视觉语言模型；
   - 文件预览：图片、PDF、表格、Office 文档；

4. **工具调用**
   - 代码执行：在隔离沙盒中执行 Python 代码；
   - 命令执行：受限的终端命令执行；
   - 子智能体调度：复杂任务交给子智能体处理；
   - 时间获取、对话中断等基础工具。

5. **搜索与扩展能力**
   - 多源网络搜索；
   - 图片解析、数据分析等技能包。

6. **可视化与前端**
   - Markdown 渲染、代码高亮、数学公式；
   - 网页预览（独立窗口）；
   - 主题切换（明 / 暗）；
   - 响应式布局。

7. **管理功能**
   - 定时清理：清理过期沙盒容器、临时文件；
   - 手动触发清理任务；
   - 清理状态查询。

#### 2.2.2 软件不包含的功能

- **多用户系统**：本系统为单机版本，不涉及多用户注册、权限管理、租户隔离；
- **企业级单点登录**：不集成 LDAP、OAuth 等企业身份认证；
- **数据可视化大屏**：不提供 dashboard 式的可视化大屏；
- **完全离线 LLM**：默认依赖在线 LLM 服务，可配置为本地模型但推理性能受限；
- **付费与计费系统**：不涉及付费、积分、计费相关功能。

### 3.2 技术可行性

#### 3.2.1 技术选型评估

| 技术 | 选型理由 | 风险 | 应对策略 |
|------|----------|------|----------|
| **多智能体框架（LangGraph 类）** | 业界主流 Agent 框架，支持循环 / 中断 / 检查点 | 学习曲线陡 | 借助官方文档与示例 |

| **Docker** | 沙盒隔离的行业标准 | 容器开销 | 预启动池化抵消 |

| **开源 VL 模型（如 Qwen-VL）** | 开源本地 VL 模型 | 推理慢 | 仅用于图片理解 |
| **OpenAI 兼容 API** | 多服务商兼容 | 厂商差异 | 适配层处理 |

#### 3.2.2 技术难点分析

1. **多智能体编排**
   - 难点：状态图框架的调试、可视化；
   - 解决方案：模块化提示词、独立节点日志。

2. **容器沙盒安全**
   - 难点：容器逃逸、资源滥用；
   - 解决方案：tmpfs 隔离 + 超时 + 白名单库。

3. **流式响应**
   - 难点：SSE 协议在反向代理后的可靠性；
   - 解决方案：标准 `text/event-stream` + `\n\n` 分隔。

4. **多模态解析**
   - 难点：不同格式的解析器切换；
   - 解决方案：加载器按后缀分流。

#### 3.2.3 技术可行性结论

✅ **技术可行**：所选技术均为业界成熟方案，关键难点已有可行的应对策略；开发团队具备 Python + Vue + Docker 全栈开发能力。

## 第8章 非功能需求

### 8.1 性能需求

| 编号 | 需求 | 指标 | 优先级 |
|------|------|------|--------|
| NFR-P1 | 首 token 延迟 | ≤ 2s（不含工具调用） | 高 |
| NFR-P2 | 流式响应连续性 | 每 200ms 内至少推送一次 | 高 |
| NFR-P3 | 单次工具执行超时 | 限时 | 高 |
| NFR-P4 | 沙盒容器池大小 | ≥ 2，并发安全 | 高 |
| NFR-P5 | 文件上传大小 | ≤ 50 MB | 中 |
| NFR-P6 | 文件解析时间 | ≤ 60s（PDF ≤ 50 页） | 中 |
| NFR-P7 | 并发会话数 | ≥ 10 | 中 |
| NFR-P8 | 首屏加载时间 | ≤ 3s | 中 |

### 8.2 安全性需求

| 编号 | 需求 | 说明 |
|------|------|------|
| NFR-S1 | 容器沙盒隔离 | 所有 Python 代码必须在容器内执行，禁止在宿主机直接运行 |
| NFR-S2 | 危险命令拦截 | rm -rf /、fork 炸弹、注册表写入等高危操作必须拦截 |
| NFR-S3 | 脚本执行拦截 | 脚本执行需二次确认或拦截 |
| NFR-S4 | 文件路径校验 | 上传文件路径必须校验，禁止路径穿越 |
| NFR-S5 | API 鉴权 | 当前为单机版预留接口，未来可扩展 JWT |
| NFR-S6 | 容器资源限制 | 单容器 tmpfs 64m noexec，超时 kill |
| NFR-S7 | 日志脱敏 | 禁止在日志中打印 API Key、密码 |

### 8.3 可用性需求

| 编号 | 需求 | 说明 |
|------|------|------|
| NFR-U1 | 主题切换 | 支持明 / 暗主题 |
| NFR-U2 | 响应式布局 | 支持常见桌面分辨率 |
| NFR-U3 | 快捷键 | 提供发送、停止等常用快捷键 |
| NFR-U4 | 错误提示 | 所有错误必须有友好提示 |
| NFR-U5 | 离线提示 | 网络断开时提示用户 |

### 8.4 可维护性需求

| 编号 | 需求 | 说明 |
|------|------|------|
| NFR-M1 | 模块化 | 后端按职责拆分 ≥ 8 个模块 |
| NFR-M2 | 日志规范 | 所有模块通过统一的日志管理器记录 |
| NFR-M3 | 配置外置 | 所有配置支持 JSON 文件 + 环境变量 |
| NFR-M4 | 类型注解 | Python 代码类型注解覆盖率 ≥ 80% |
| NFR-M5 | 注释覆盖 | 核心算法必须有详细注释 |

### 8.5 可移植性需求

| 编号 | 需求 | 说明 |
|------|------|------|
| NFR-PT1 | 跨平台 | 后端支持 macOS / Linux / Windows |
| NFR-PT2 | 桌面端 | Electron 打包支持三大桌面平台 |
| NFR-PT3 | 容器化 | 支持 Docker Compose 一键启动 |

## 第10章 数据约束与限制

### 10.1 数据量限制

| 项目 | 限制 | 说明 |
|------|------|------|
| 单文件大小 | ≤ 50 MB | 文件上传限制 |
| PDF 页数 | ≤ 50 页 | 解析性能保证 |
| 单会话消息数 | ≤ 1000 条 | 性能保证 |
| 单会话检查点数 | ≤ 100 个 | 回溯性能 |
| 沙盒容器池 | 2 个 | 资源占用平衡 |
| 记忆文件大小 | ≤ 1 MB | 单会话记忆上限 |

### 10.2 数据保留策略

| 数据类型 | 保留时长 | 处理方式 |
|----------|----------|----------|
| 会话数据 | 永久（用户主动删除） | Redis + 检查点 |
| 上传文件 | 永久（用户主动删除） | 本地缓存目录 |
| 对象存储同步文件 | 永久（用户主动删除） | 第三方对象存储 |
| 临时沙盒文件 | 单次执行结束 | 立即清理 |
| 日志文件 | 30 天 | 自动滚动 |

### 10.3 数据一致性约束

1. **会话与消息一致性**：删除会话时级联删除所有消息和检查点；
2. **记忆与状态一致性**：回溯时同步重建记忆；
3. **对象存储与本地一致性**：上传成功后立即同步，断网时降级为本地模式；
4. **检查点与状态一致性**：每轮结束保存检查点。
